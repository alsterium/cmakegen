# T019 research — filesystem Unicode equivalence capabilities

## Date

2026-08-12

## Findings

- The portable rule remains independent of the host: ASCII case aliases and
  Win32 component trailing-dot/space aliases are handled locally and are not
  inferred from the host filesystem.
- macOS exposes volume format capabilities through `getattrlist` and
  `vol_capabilities_attr_t`; `VOL_CAP_FMT_CASE_SENSITIVE` describes whether
  upper/lower case names are distinct. Apple’s APFS reference documents APFS
  as preserving filename case and normalization while being normalization
  insensitive, and supporting case-sensitive and case-insensitive variants.
  The implementation therefore recognizes only the detected `apfs` and `hfs`
  volume families for additional Unicode comparison and uses Core Foundation
  Unicode normalization/case folding as a conservative comparison key.
- Windows exposes volume case-search support with `GetVolumeInformationW`.
  Windows also has per-directory case sensitivity, so the implementation
  queries `FileCaseSensitiveInfo` when the API is available and treats a
  failed/unsupported query as indeterminate rather than assuming a mode.
  Unicode case comparison uses `CompareStringOrdinal`, not a user locale.
  Windows ordinal comparison deliberately does not treat canonically
  equivalent Unicode sequences as equal, so normalization is not added to the
  Windows key.
- `std::filesystem::equivalent` is useful only when both names already resolve
  to existing filesystem objects; it cannot establish collision safety for two
  new output names. It remains a fallback signal during existing-directory
  alias resolution, while output/manifest comparisons use the detected
  capability.
- Apple `getattrlist` returns a leading total-length field before the requested
  attribute payload; capability reads must account for that prefix. The
  Windows `FILE_INFO_BY_HANDLE_CLASS` value for `FileCaseSensitiveInfo` is 23
  in the documented enumeration.

## Safety decision

If a path contains non-ASCII bytes and the target filesystem’s Unicode
capability cannot be detected or is not supported, SafeWriter fails preflight
with a filesystem diagnostic. It never falls back to the process locale or
silently claims collision safety. The portable ASCII/Win32 equivalence remains
active even when Unicode capability detection is unavailable.
